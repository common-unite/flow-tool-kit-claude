# Decisions, in the order they constrain each other

Moved from this skill's SKILL.md, read on demand: Decisions, in the order they constrain each other.

## Decisions, in the order they constrain each other

1. **Experience plan.** Audience, the form's kind (`form_kind`) and its row in the form-type rules. The row sets the header, buttons, indicator, page headings and first page; `draw_plan.py` writes those settings, so you only choose the kind. **Keep the source's page structure**: a one-page form stays one page. Offer a different structure as a question, never as the design. Keep requiredness, stored values, conditions, calculations and consent text exactly. A required flag you want to change is a question for the person; record the answer as the field's `required_change` (the check lists every difference).
2. **Field shape**, row by row against the source: a combined field stays one field; a single-select stays single-select with the source's options and words; only the parts of a block the source asks; a repeating block becomes a `Repeater`; every consent stays, one per section; a link in a consent stays in the text. A component that asks more or less than the source is a question, not the design.
3. **Placement and the mapping preference** (`_shared/standards/mapping-preference.md`). On a **paid** org, a question about a record of a known object (name, email, phone, organization, address) goes on a component built on that object (Contact, Account, the partner's own object), with **Form Template Mapping** mapping each field to the Form Submission field it stands for (the packaged Contact 1 and Account fields first). The conversion's Apply Submission Field Maps then fills those fields; hand-built Transform rows are only for calculated or combined values, Campaign Members and record types. A new Form Submission field only when no packaged one fits, listed in `questions`. On a **free** org, components stay on Form Submission (free forms work only on Form Submission, Account, Contact, Lead and Case), and new-mapping-flow maps each answer. Long answers, rich text, survey responses and fields that drive the form stay on Form Submission in both editions. Placement text starts `source-object:`, `mapped:` or `submission:` with the reason.
4. **Components, the reuse question and the shape.** Reuse is about Form Components, the blocks of questions placed in the sections of many Form Templates; a Form Template is this one whole form. Compare every section with the org catalog. When a catalog component matches (same object and most of the same fields, or the same purpose), **ask, naming it**: "Reuse *Contact Details* as is, extend it with *Website*, or build a new component?" Ask every match in one message, each with your recommendation. Never reuse, extend or duplicate silently. Record the match in `catalog_match` and the answer in `asked`; `draw_plan.py` stops on a match with no answer. Decisions: `reuse`, `extend` (a new version of the existing component under its own `new_name`, plus `add_fields`; the original and everything using it stay as they are), `shared-new`, `form-only`, `flow-section`, `custom-lwc`. Changing the original in place is `update`: never the default and never part of the reuse question. Offer it only as its own question that names every template and component it reaches, and only for a component the org can edit (a packaged component is extended instead). The canvas tags it above the section. Section boundaries follow build-form-component's guidance; a header whose words change per form lives on the page section, never in the component.
   - **The shape**, for every `form-only`, `shared-new` and `extend` component ([_shared/standards/component-shapes.md](../_shared/standards/component-shapes.md)): **JSON on the section** by default, the easiest and free of conflicts with shared components; **one record component**, built right away and referenced by every place, only when reuse is known at design time (the plan places the same block in more than one section, Repeater or form, even within one form, such as a main contact section and a Repeater for additional contacts, or the catalog shows the same questions built in place on other templates); **metadata** is not recommended for new work and comes later through convert-to-metadata, or when the person asks. An `extend` keeps the original's shape. Reuse found later is consolidated then, never guessed up front. Recommend one with the reason (org-catalog's `match` gives a recommendation per section), name the alternatives, and ask in the same message as the reuse question. Record `shape` and `shape_asked` (`_shared/standards/plan-format.md`); `draw_plan.py` stops on a shape that was never asked. `reuse` and `update` keep the existing component's shape. A plan from before shapes still draws, with a warning, and builds as it always did.
5. **Escape hatches.** For every custom script, calculation or workaround the source reports, pick in order: a native control or setting; a **Flow Section** (`decision: flow-section`, `build: build-flow-section`, section `Component_Type__c` `Flow` with `FlowApiName__c`) for logic a flow does better, such as lookups, branching on org data or calculations across records; a **custom LWC section** (`decision: custom-lwc`, `build: build-custom-lwc`, `Component_Type__c` `Lightning Web Component` with `lwcComponentName__c`) for an interaction no control covers. Drop source-only plumbing (spam timers, its own script hooks) and say so. Offer each Flow Section or custom LWC as a named add-on in `questions`: what it does, why the template alone cannot, and that it is a small build. The canvas draws it as a marked placeholder; those skills build it after the template.
6. **Layout.** Controls from the data type first, widths from the expected answer (first name narrower than last name, email wider than phone, phones 12), frames, headers and dividers by the house rules.
7. **Copy**, in the organization's voice (the brand kit's tone and the program page's words when there is a kit):
   - every page a `Description__c` of at least two sentences (what the page asks, then why or what to have ready), every titled section a one-line subtitle; untitled sections only for a follow-up or a note on a highlight bar;
   - button labels only from the package's lists (`_shared/standards/plan-format.md`); the forward button reads Continue, never Next; no page labelled Welcome; no "Page N of M";
   - a confirmation message of two or three tailored paragraphs: thanks, why it matters, what happens next and when, a contact (a `[placeholder]` listed in `questions` when unknown);
   - an inactive message that says the form is closed and how to reach the organization;
   - unknown facts as `[bracketed placeholders]`, each in `questions`; merge fields `{{Field_API_Name__c}}`; no em-dashes; no field names in respondent copy.
8. **Emails**, designed on the canvas before anything is built (Lightning Email Templates on Form Submission, merging direct Form Submission fields only):
   - a confirmation email for every form that collects an email (`emails.confirmation`);
   - a long form in stages mode: `emails.resume`, the **Email me a resume link** button's email (`Email_Template_Name_Resume_Form__c`);
   - an ordinary form with Save Progress on: `emails.saved`, the Save Progress email (`Email_Template_Name_Saved__c`), which goes out on its own when the respondent saves;
   - both resume emails merge **`{{FlowToolKit__Internal_Resume_Link__c}}`** (Save Progress Resume Link) for the button. The package builds that link from the template's web form address; never build a link by hand with `pv9` or `recordId`, and no URL Parameter Mapping is needed.
9. **Surveys and anonymity.** A survey question section is a **Survey Section** (`Survey_Section__c`, one question card at a time); a grid of statements is a Likert section. Turn on **Enable Form Analytics** when the organization wants charts and reports of the answers. An anonymous survey adds the packaged **Anonymous** field (`FlowToolKit__Anonymous__c`): ticking it hides and clears identifying sections and fields and skips Contact and Lead creation, and the package sends no confirmation email for it. Truly anonymous means a public site's guest link for everyone, Save Progress, Autosave and the Save Progress email off, and no file uploads; a signed-in respondent is still recorded as the record's creator, so tell the person.
10. **The answers PDF.** A long form attaches a PDF of the answers to its confirmation email (`Attach_PDF_Confirmation__c`; the build sets the conversion's running user it needs). Sections with nothing to show (all questions hidden, an empty repeater) are left out of the PDF on their own, so Do Not Print is not needed for that. When the source has a printed layout of its own, offer a **DynamicPDF** page with Form Components and the Generate PDF action as an add-on in `questions`; it is a separate build, not a form setting.
11. **Support status** per field: `supported`, `verify` or `gap`, with the exact behavior a gap needs in `gaps`. The person must not approve something the package cannot deliver.
